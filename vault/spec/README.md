# Project spec

`gubia` is a loop engine that drains markdown task plans: it locates
the next pending subtask, injects it with a fixed contract into a CLI
agent, captures its exit code, and rotates models on failure. This
folder is the project spec, written against the live code of the repo.

## Spec map

| File | What it documents | Source of truth |
|---|---|---|
| [motor.md](motor.md) | engine decisions and contract: CLI, local state, rotation, process management, script structure | `gubia` (executable, 2172 lines) |
| [catalogo.md](catalogo.md) | global agent catalog: models, fallback lists, contract of the `agent_*` functions, `agent_probe` | `config/agents.sh` |
| [instalacion.md](instalacion.md) | installation and sync: projecting skills to harnesses, `install-config`, `config validate` | `justfile` |

These three files replace the historical v1 spec (stale: ~550 lines,
nonexistent layers, outdated counts). Every fact is anchored to the
live file it cites, not copied from the historical version.

## Engine / skill boundary

There are two distinct `gubia`s, and pinning down that distinction is
this section's purpose:

- **The `gubia` binary** (repo root) is the **engine**: a bash monolith
  that drains the plan. It knows nothing about any particular domain;
  it only locates `- [ ]`, injects the contract, and captures the
  result. Its write authority is the local state (`.gubia/state.env`),
  never the plan.
- **The `gubia` skill** (`skills/gubia/`) is **operational knowledge for
  the agent**: instructions on how to manage the loop from inside an
  iteration (drafting the plan, launching the engine, watching it). The
  engine doesn't read it; the agent running the iteration reads it, and
  only because the injected contract names it. `just sync-skills`
  projects it to each harness's layout (see `instalacion.md`).

The binary drains the plan; the skill tells the agent how to
participate in the draining. They share no code: one is
infrastructure, the other is instructions.

## Where each artifact lives

| Artifact | Path in the repo | Scope |
|---|---|---|
| Engine (binary) | `gubia` | per repo (linked to `~/.local/bin/gubia` by `install-config`) |
| Agent catalog | `config/agents.sh` | per repo (copied to `~/.config/gubia/agents.sh` by `install-config`) |
| Operational skills | `skills/{gubia,judge,scribe}/` | per repo (projected to each harness by `sync-skills`) |
| Local state | `.gubia/state.env` | per repo, generated by the engine |
| Iteration logs | `.gubia/logs/<iter>.{prompt,out,err,console}` | per repo, generated by the engine |
| Plan lockfile | `.gubia/<slug>.lock` | per plan, generated by the engine |
| Plan and tasks | `plan/plan.md`, `plan/task/*.md` | per repo, written by the agent |
| Project spec | `vault/spec/` (this folder) | per repo |

The catalog and the skills live versioned in the repo and are
**projected** to the user's machine unidirectionally (sync/copy): the
repo is the source, the machine is the copy. State and logs are
generated by the engine in `.gubia/` and are not versioned.
