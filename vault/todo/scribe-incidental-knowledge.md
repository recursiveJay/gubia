# `scribe` documents incidental repo state as durable knowledge

> `scribe`'s classification step never filters one session's incidental state from
> reusable knowledge, so it writes the former into the vault.

## Problem

`scribe`'s classification step (`skills/scribe/review.md`,
Step 2.3) sorts every surviving finding into `create`/`extend`/`delete`
purely by novelty against the existing inventory — it never asks whether
the finding is *reusable knowledge* (a methodology, a pitfall, or a design
decision that would still matter in a different repo state or session) or
just a *narration of this session's incidental circumstances* (e.g. "there
happened to be unrelated uncommitted WIP in this exact file at this exact
moment"). The PLAN subagent (`review.md`, "PLAN") feeds this gap: it is
instructed to report "decisions documented explicitly in the task file
itself" with no filter for whether the decision generalizes past the one
git state it was made in.

## Observed symptom

Commit `8d48c2b` ("vault: document hunk-granularity
staging for catalog edits") extended
`vault/knowledge/agent-invocation-and-catalog-in-gubia.md` with a paragraph
anchored to one specific incident: `config/agents.sh` happened to carry
unrelated, uncommitted model-name WIP while task 01's `--respect-workspace-trust`
fix landed in the same file, so the fix was staged with `git add -p`
(commit `4bd9e78`, "2 insertions") instead of `git add -A`. That fact is
true only about that one moment of that one working tree; a future reader
of the vault gains nothing actionable from it that isn't already covered by
plain git hygiene ("don't stage unrelated changes together"). It reads as
what an agent did given the state it found, not as project knowledge.
Contrast with the "Preventive guidance" paragraph immediately after it in
the same file (grep test files for hardcoded model names before editing
`config/agents.sh` model lists) — that one *is* a reusable methodology: it
holds regardless of what the working tree looks like on a given day.

## Done when


- `skills/scribe/review.md` Step 2 gains an explicit filter, applied before
  classifying into `create`/`extend`/`delete`: for each surviving finding,
  ask "would this be true or relevant in a different repo state or a
  different session, or does it only narrate what this session's working
  tree happened to contain right now?" Findings that are pure incidental
  narration (a transient `git status`, a one-off staging choice driven by
  someone else's unrelated WIP) are discarded, not written — even if they
  came from a real, well-evidenced observation.
- The same filter note clarifies that a finding can be *partially* reusable:
  when a narrated incident contains an embedded generalizable rule (as
  `8d48c2b` did, buried inside the incident-specific paragraph), `scribe`
  extracts and keeps only the generalizable rule, phrased without reference
  to the specific commit/session that prompted it — not the incident
  narrative around it.
- `vault/skills/scribe/review.md` (the hand-maintained mirror, per
  [[sync-skills-replace-by-directory]]) is updated in lockstep with the same
  wording, not regenerated by copying.
- A short "reusable vs. incidental" example pair is added to `review.md`
  itself (or referenced from it) so the distinction survives being read out
  of context — e.g. contrasting `8d48c2b`'s incident paragraph (discard) against
  its own neighboring "Preventive guidance" paragraph (keep) as the
  canonical positive/negative pair.
- Re-running `scribe review` against a similar future scenario (unrelated
  WIP found mixed into an in-scope file) produces no new `vault/knowledge`
  entry about the incident itself, only — if anything — a generalized
  methodology entry if one does not already exist.
